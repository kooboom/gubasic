# 알려진 문제

[English](KNOWN_ISSUES.md)

알고 있지만 지금은 **일부러** 고치지 않은 문제를 적어 둡니다. 항목마다 무엇인지, 왜 미뤘는지, 언제 다시 볼지를 적습니다. 문제를 고치면 같은 변경에서 항목을 지웁니다.

---

## 아주 긴 반복이 느림

- **무엇:** 100만 번 도는 반복(`total = total + i * 2 - 1`)이 인터프리터가 시간으로 쉬게 된 뒤(STAGE2_PLAN §7) Chrome의 플레이어에서 약 3.3초, WebKit에서 1.1초, macOS 플레이어에서 1.3초 걸립니다. 그 전에는 7.5초, 7.1초, 1.4초였습니다.
- **왜 미뤘나:** 정확성 문제가 아니고, 초보자가 쓰는 프로그램 규모에서는 체감되지 않습니다.
- **다시 볼 때:** 놀이터나 IDE에서 실제로 느리다는 사례가 생길 때. 2-2 단계가 플레이어에서 재고 트랜스파일러를 다시 볼 기준을 정합니다(STAGE2_PLAN §7, D79).

## 놀이터는 폼을 실행하지 않음

- **무엇:** 폼은 IDE의 실행 창(`apps/ide`)과 동일성 테스트에서 실행되지만, 놀이터는 폼이 없는 프로그램만 실행합니다. 놀이터에서는 여전히 컨트롤과 `Me`를 알립니다(A003).
- **왜 미뤘나:** 놀이터는 Flutter 없는 순수 Dart이고, HTML로 컨트롤을 흉내 내면 두 번째 런타임이 생깁니다(D24). 브라우저에서는 대신 IDE의 웹 빌드(E1e)가 폼을 실행합니다.
- **다시 볼 때:** IDE의 웹 빌드를 게시할 때. 그때 놀이터에 실행 탭이 여전히 필요한지 정합니다.

## 웹 IDE가 브라우저에 보관한 프로젝트는 사라질 수 있음

- **무엇:** 웹에서는 프로젝트를 브라우저의 IndexedDB에 보관합니다(D33, D53). 브라우저 데이터를 지우면 함께 사라지고, 공용 PC는 로그아웃할 때마다 지울 수 있으며, Safari는 7일 동안 방문하지 않으면 지웁니다. 같은 프로젝트를 탭 두 개에서 열면 마지막에 저장한 쪽이 남습니다.
- **왜 미뤘나:** 웹 페이지는 스스로 디스크에 파일을 보관할 수 없습니다. IDE는 `.zip` 내려받기를 한 번에 누를 수 있게 두고, 내려받지 않은 변경이 있는 동안 내려받으라고 알리며, 처음 저장할 때 이 점을 알립니다.
- **다시 볼 때:** 사용자가 실제로 작업을 잃을 때. 그때 브라우저가 허용하는 곳에서는 폴더에 저장하는 방법(File System Access API, Chrome과 Edge만)을 검토합니다.

## 웹 IDE의 페이지가 닫힐 때의 변경은 아직 잃을 수 있음

- **무엇:** 변경은 잠시 뒤 IndexedDB에 보관되고, 페이지가 가려지거나 떠날 때는 텍스트를 `localStorage`에도 써서 다음 시작 때 되살립니다(D54). 그래도 다음 경우에는 잃을 수 있습니다.
  - 페이지가 `visibilitychange`나 `pagehide` 없이 끝날 때: 브라우저나 운영체제가 멈추거나, 전원이 나가거나, 휴대폰이 두 신호 없이 탭을 끝낼 때. 마지막으로 끝난 쓰기 뒤의 변경(약 2초 동안의 작업, 쓰기가 실패하는 동안이면 더)을 잃습니다.
  - `localStorage`가 가득 찼거나 꺼져 있을 때: 임시 기록을 쓰지 못하고, 페이지가 닫히는 중이라 알리지도 못합니다.
  - 페이지가 닫힐 때 그림을 넣거나 빼는 중이었을 때: 그림은 바로 보관하지만(D54) 그 쓰기가 끝나지 않으면, 되살린 텍스트가 보관되지 않은 그림을 적게 됩니다. IDE는 어떤 그림인지 알립니다.
  - 같은 프로젝트를 탭 두 개에서 열었을 때: 저장과 마찬가지로(위 항목) 마지막에 가려진 탭의 임시 기록이 남습니다.
- **확인한 것:** Chromium에서 쓰기를 붙잡은 채 탭을 닫았을 때, WebKit에서 쓰기가 커밋되지 않는 채 새로고침했을 때 모두 변경이 되살아났습니다(Playwright, 배포 빌드). Safari 27.0.1에서는 로컬 서버의 배포 빌드로 변경 직후 탭을 직접 닫았고, 변경이 지켜졌습니다. 다만 보통 경로로 지켜졌습니다. IDE는 내려받지 않은 변경(아직 보관하지 않은 변경 포함)이 있으면 늘 떠날지를 묻게 하므로 Safari가 물었고, 묻는 사이 2초 자동 보관이 끝나서 되살릴 것이 남지 않았습니다. **확인하지 못한 것:** Safari에서 탭이 닫힌 뒤 변경을 되살리는 경로 자체, 곧 보관이 끝나기 전에 닫히는 경우. Playwright의 WebKit은 빈 페이지에서도 페이지를 닫을 때 `pagehide`도 `visibilitychange`도 보내지 않아서, 이것으로도 확인할 수 없습니다. 또 Playwright의 WebKit(1.56)은 새로고침이나 페이지 이동 때 가끔 페이지가 멈췄고(`main`에서도 같음), Safari도 그런지는 알지 못합니다.
- **왜 미뤘나:** 페이지는 닫히는 것을 늦출 수 없고, 페이지가 쓸 수 있는 곳 가운데 `localStorage`보다 크면서 동기인 곳은 없습니다.
- **다시 볼 때:** Safari에서 보관보다 먼저 닫히게 할 수 있을 때(마지막 변경 후 2초 안에 「떠나기」 고르기): 변경이 안내와 함께 되살아나는지 확인합니다. 그리고 사용자가 작업을 잃었다고 알려 올 때.

## 실행 창이 IDE 창 안에 있음

- **무엇:** 실행 중인 프로그램의 폼은 따로 된 창이 아니라 IDE 창 가운데에 나타납니다. 모서리로 크기는 바꿀 수 있지만(D59), 폼을 옮기거나 프로그램 둘을 나란히 실행할 수는 없습니다.
- **왜 미뤘나:** 창 하나로 하면 데스크톱과 웹에서 똑같이 동작합니다. 창을 따로 띄우려면 데스크톱 운영 체제마다 플랫폼 코드가 필요합니다.
- **다시 볼 때:** 폼 디자이너와 함께 IDE의 창 배치를 정할 때.

## 한글 입력은 아직 Chrome에서만 시험함

- **무엇:** TextBox 테스트는 Chrome에서 Windows 한글 입력기와 macOS 한글 입력기(두벌식)가 보낸 신호를 재생합니다(`packages/gubasic_runtime/test/ime_logs/`). 데스크톱 앱은 아직 실제 입력기로 시험하지 않았습니다. macOS는 IDE 실행 창과 함께 시험합니다. Windows 앱은 CI가 빌드하므로 아무것도 설치하지 않고 내려받아 실행할 수 있습니다(D47). 그래서 학교 PC에서 기록할 수 있습니다.
- **두 기록에서 본 것:** 둘 다 LANGUAGE 11.1절의 약속을 지킵니다. 다섯 시나리오 모두에서 같은 이벤트를 만들었습니다. 스페이스는 앞 음절과 함께 확정되므로, 닭 다음에 `Changed`는 `닭 `은 보지만 `닭`만 따로는 보지 않습니다. 도중의 신호만 다릅니다(macOS는 스페이스를 먼저 조합 안에 넣습니다). 둘 다 입력 칸이 포커스를 잃을 때 조합 중인 글자를 확정하며, 웹에서는 클릭보다 150~180 ms쯤 먼저입니다.
- **그때 확인할 Flutter 문제:** Windows 데스크톱에서 빠르게 치면 음절이 빠지는 문제([flutter/flutter#189491](https://github.com/flutter/flutter/issues/189491), 열림). 웹에서 브라우저가 조합을 버리면 조합 범위가 남는 문제([flutter/flutter#193847](https://github.com/flutter/flutter/issues/193847))는 Flutter master에서 고쳤지만 3.47.7에는 없습니다. 두 Chrome 기록 모두에서 생기지 않았습니다. 입력 칸을 떠날 때 글자가 깨끗하게 확정되었습니다.
- **왜 미뤘나:** 기록하려면 사람이 시스템마다 직접 쳐야 합니다.
- **다시 볼 때:** 학교 PC에서, CI가 만든 Windows IDE와 입력기 기록 도구로(D47, 단계는 이슈 #14).

## 나중에 만든 앱에서 IDE에서 그린 글자가 잘릴 수 있음

- **무엇:** 런타임은 글꼴을 고르지 않으므로(DESIGN 2.3절), 나중에 트랜스파일러로 만든 앱은 기기의 기본 글꼴을 씁니다. IDE는 담아 온 Pretendard를 씁니다(D30). 그러면 출시된 앱의 글자 폭이 IDE와 달라져, 맞게 그린 Label의 글자가 잘릴 수 있습니다.
- **왜 미뤘나:** 트랜스파일러가 아직 없습니다. 2단계의 플레이어(D79)는 GuBASIC 자체의 앱이라 IDE의 글꼴을 담을 수 있습니다. 2-2 단계에서 그렇게 하고, 그러면 플레이어 앱은 IDE와 똑같이 글자를 놓습니다.
- **다시 볼 때:** 트랜스파일러와 함께. 선택지로는 생성 앱에도 같은 글꼴을 넣는 것(약 3 MB 커짐), 디자이너가 글자 잘림 위험을 경고하는 것 등이 있습니다.

## 웹 IDE의 글꼴 불러오기는 학교망에서 확인하지 않았습니다

- **무엇:** 외부 주소를 모두 막고(headless Chrome, `--host-resolver-rules="MAP * ~NOTFOUND, EXCLUDE 127.0.0.1"`, 웹 빌드를 로컬 서버로 띄움) 열었을 때, IDE의 한국어 문구가 바르게 나오고 페이지가 외부에서 받는 것이 없었습니다. 엔진, 글꼴, 대체 글꼴 모두 로컬 서버에서 왔습니다. macOS와 Windows(Chrome 155)에서 확인했습니다. 넷 로그에 남은 외부 요청은 업데이트, 맞춤법 사전처럼 Chrome이 스스로 보낸 것뿐이었습니다. 음절이 □로 빠지는 문제([flutter/flutter#188255](https://github.com/flutter/flutter/issues/188255))는 나타나지 않았습니다.
- **느린 네트워크에서 첫 방문**(Windows, headless Chrome, 캐시 끔, DevTools의 Slow 4G 설정: 지연 562.5 ms, 180 kB/s, 127.0.0.1에서 받음): "불러오는 중…"이 1.1초부터 약 102초의 첫 화면까지 보였습니다. Noto Sans KR 두 파일이 100.3초와 101.3초에 도착했고, 첫 화면은 그 바로 뒤에 그려졌습니다. 모든 프레임을 화면 녹화(screencast)로 보니 불러오는 중 문구에서 Noto Sans KR로 다 그려진 IDE로 바로 넘어갔습니다. 다른 글꼴로 그린 프레임이 없었으므로, 처음에 다른 글꼴로 그렸다가 바로잡히는 문제([flutter/flutter#77023](https://github.com/flutter/flutter/issues/77023))는 나타나지 않았습니다. `typing`을 실행하고 TextBox에 동해물과 백두산이 닭 값을 넣었을 때 TextBox와 Label 모두 □ 없이 나왔습니다.
- **Pages 주소에서**(E1e, https://kooboom.github.io/gubasic/ide/, 다른 호스트를 모두 막은 macOS의 headless Chrome): IDE가 열렸고, 모든 파일이 kooboom.github.io에서 왔습니다. 크기는 D30에 있습니다.
- **왜 미뤘나:** 학교망을 거치지 않았습니다. 그러려면 학교 PC가 필요합니다.
- **다시 볼 때:** 학교 PC에서 이슈 #14의 단계대로: 학교망의 보통 브라우저로 주소를 열고 첫 방문에 걸리는 시간을 잽니다.

## 불러오는 중 퍼센트는 Firefox에서 확인하지 않았습니다

- **무엇:** 웹 IDE의 "불러오는 중… 37%"(D43)는 Chrome과 WebKit(Safari의 엔진)에서 확인했습니다(Playwright 1.56, 로컬 서버, 느린 망 흉내). 퍼센트가 94~99%까지 오르고 첫 화면과 함께 사라졌으며, 모든 파일을 한 번씩만 받았습니다. Firefox는 확인하지 못했습니다. Playwright의 Firefox(142)가 이 macOS에서 시작되지 않고, Firefox도 설치되어 있지 않습니다. Firefox는 자체 엔진인 Gecko에서 돌아가므로([MDN](https://developer.mozilla.org/en-US/docs/Glossary/Gecko)) Chrome과 WebKit의 결과로 대신할 수 없습니다. Safari와 같은 점은 Flutter 로더가 고르는 빌드 하나뿐입니다. Chrome의 `Intl.v8BreakIterator`가 없으므로 Chromium용이 아니라 전체 CanvasKit 빌드를 받습니다.
- **왜 미뤘나:** 확인하려면 실행되는 Firefox가 있어야 합니다. 코드에는 특정 브라우저만을 위한 부분이 없습니다.
- **다시 볼 때:** Firefox를 쓸 수 있을 때(학교 PC, 또는 여기서 시작되는 Playwright 버전): 캐시를 끄고 IDE를 열어, 퍼센트가 오르는지와 파일마다 한 번씩만 받는지 확인합니다.

## 웹 IDE의 글꼴은 WOFF2가 아니라 OTF로 보냅니다

- **무엇:** Pretendard는 GitHub Pages가 gzip으로 압축한 OTF 파일로 브라우저에 갑니다(Regular 1.6 MB, 전송 1.05 MB). WOFF2는 글꼴을 더 잘 압축하지만, Flutter 문서는 `.ttc`, `.ttf`, `.otf`만 적고 WOFF와 WOFF2는 데스크톱 플랫폼에서 지원하지 않는다고 하며, 웹에 대해서는 말하지 않습니다([Flutter](https://docs.flutter.dev/cookbook/design/fonts)).
- **왜 미뤘나:** IDE는 모든 플랫폼에서 글꼴 목록 하나를 쓰고(D30), 웹 지원은 문서에 없습니다. 시도하지 않았습니다.
- **다시 볼 때:** Flutter가 웹의 WOFF2를 문서에 적을 때, 또는 학교망에서 첫 방문이 여전히 너무 느릴 때.

## 줄여서 넣은 그림은 JPEG가 아니라 PNG입니다

- **무엇:** 줄여서 넣기(D56)는 PNG를 씁니다. 그래서 1024 × 768 휴대폰 사진이 1.3–1.8MB가 되어(macOS, Chrome, WebKit), 그림 하나에 허용되는 2MB에 가깝습니다. 잔무늬가 많은 사진은 다시 줄여서 768픽셀 이하가 됩니다. JPEG였다면 수백 KB였을 것입니다. Windows에서는 해 보지 않았습니다. 같은 Flutter 호출로 디코딩하고 인코딩합니다.
- **왜 미뤘나:** Flutter는 PNG만 인코딩합니다([Flutter](https://api.flutter.dev/flutter/dart-ui/ImageByteFormat.html)). JPEG 인코더는 패키지나 IDE가 직접 쓴 코드가 필요하고, 무거운 의존성은 넣지 않기로 했습니다.
- **다시 볼 때:** 사용자의 사진이 자주 1024픽셀보다 작아질 때, 또는 사진 때문에 프로젝트가 10MB 한도에 닿을 때. 그리고 학교 PC의 Windows IDE에서.

## ListBox의 항목은 코드에서만 넣을 수 있습니다

- **무엇:** Visual Basic 6처럼 속성 창의 List 속성으로 ListBox의 항목을 넣을 수 없습니다. 프로그램이 보통 `Form_Load`에서 `AddItem`으로 넣습니다(D46).
- **왜 미뤘나:** 폼 파일에 글자 목록을 담는 속성과, 한 줄에 한 항목을 쓰는 속성 창 입력란이 필요합니다. 1단계의 퀴즈는 문제마다 코드에서 목록을 채웁니다.
- **다시 볼 때:** 바뀌지 않는 항목(언제나 같은 보기 목록)이 필요한 프로그램이 생길 때, 또는 다음에 폼 파일을 바꿀 때.

## ListBox는 마우스로만 고릅니다

- **무엇:** ListBox의 항목은 클릭해서 고릅니다. 화살표 키나 글자를 쳐서 고른 항목을 옮길 수는 없습니다.
- **왜 미뤘나:** 실행 중인 폼의 컨트롤이 아직 차례로 키보드 포커스를 받지 않고(Tab), 퀴즈는 마우스로 답합니다.
- **다시 볼 때:** 실행 창의 컨트롤이 키보드 포커스를 받게 될 때(Tab으로 옮겨 다니기).

## 여러 컨트롤을 골라도 속성 창에서 함께 바꾸지는 못합니다

- **무엇:** 컨트롤을 여러 개 고르면(D97) 속성 창은 하나만 고르라고 알립니다. `Anchor`나 `Width`처럼 함께 가진 속성도 한꺼번에 바꿀 수 없습니다. 마우스로는 컨트롤 하나씩만 크기를 바꾸고, Shift와 화살표 키는 고른 컨트롤 모두의 크기를 바꿉니다.
- **왜 미뤘나:** 종류가 다른 컨트롤이 어떤 속성을 함께 가지는지, 값이 서로 다를 때 무엇을 보일지는 따로 정할 규칙입니다. 여러 컨트롤로 하는 일은 대부분 옮기기, 지우기, 순서 바꾸기, 복사, 붙여넣기로 됩니다.
- **다시 볼 때:** v0.4의 입력 화면처럼 같은 종류의 컨트롤이 많은 폼에서 불편해질 때.

## 디자이너의 클립보드는 따로 있습니다

- **무엇:** 디자이너에서 복사하거나 잘라 낸 컨트롤(D97)은 시스템 클립보드가 아니라 IDE 안에 남습니다. 다른 IDE 창에 붙여 넣거나 다른 프로그램에 글로 붙여 넣을 수 없고, IDE를 닫으면 사라집니다.
- **왜 미뤘나:** 브라우저는 페이지가 클립보드를 읽기 전에 사용자에게 묻고, 다른 곳에서 붙여 넣은 글은 폼 파일처럼 검사해야 합니다(F 코드).
- **다시 볼 때:** IDE 창 둘을 나란히 쓸 때, 또는 데스크톱에서 창이 따로 열릴 때(D89).

## 컨트롤은 디자이너에서만 Frame에 넣습니다

- **무엇:** 프로그램은 컨트롤을 Frame에 넣지 못합니다(D105). Frame에는 자기 `Controls`가 없어서 `Me.Controls.Add`는 컨트롤을 폼에 바로 놓고, Frame에서 뺐다가 다시 넣은 컨트롤도 폼에 놓입니다. 컨트롤을 담은 Frame은 뺄 수 없습니다(R023). 디자이너에서는 끌어도 컨트롤이 Frame 안에 머물고, 잘라 내고 붙여 넣어야 들어가거나 나옵니다.
- **왜 미뤘나:** Frame의 `Controls`와 Frame 안팎으로 끌기는 규칙(어느 Frame에 놓는 것인지, Anchor는 어떻게 되는지)을 더하는데, Frame을 쓰는 첫 프로그램들에는 필요하지 않습니다.
- **다시 볼 때:** 프로그램이 실행 중에 Frame의 내용을 만들거나, 사용자가 컨트롤을 Frame에 끌어 넣기를 바랄 때.

## macOS 메뉴는 Checked를 ✓로 보이고, 메뉴 편집기는 처리기 이름을 바꾸지 않습니다

- **무엇:** macOS 메뉴 막대(D106)에서 Checked 항목은 시스템의 체크 표시 자리가 아니라 Caption 앞에 ✓를 붙여 보입니다. 메뉴 편집기에서 항목 이름을 바꿔도, 속성 창에서 컨트롤 이름을 바꿀 때(D39)와 달리 코드의 처리기 이름은 바뀌지 않습니다. Caption의 `&`는 그대로 보이며, 아직 접근 키(Alt와 글자)는 없습니다.
- **왜 미뤘나:** Flutter의 플랫폼 메뉴는 시스템에 체크 표시를 보내지 않습니다. 코드 속 이름 바꾸기와 접근 키는 메뉴 편집기와 메뉴를 그리는 세 방법 모두에 더할 일인데, 메뉴를 쓰는 첫 프로그램들에는 필요하지 않습니다.
- **다시 볼 때:** Flutter의 플랫폼 메뉴가 체크 표시를 받을 때, 사용자가 이름 바꾸기나 접근 키를 바랄 때.

## TextBox가 쓰는 키는 폼에 오지 않습니다

- **무엇:** `KeyPreview`가 True이고 TextBox에 입력하는 동안, 폼은 TextBox가 글자로 치는 키(글자, 숫자, Space)만 받고, 화살표 키, Home, End처럼 TextBox가 커서를 옮기는 데 쓰는 키는 받지 않습니다(D101).
- **왜 미뤘나:** Flutter의 글 입력 칸이 폼보다 먼저 그 키를 가져갑니다. 폼이 먼저 보게 하려면 모든 입력 칸에서 그 키를 넘겨받아야 합니다.
- **다시 볼 때:** 그 키가 필요한 프로그램이 생길 때, 또는 메뉴의 단축키와 함께.

## 폼 디자이너는 마우스가 있어야 합니다

- **무엇:** 컨트롤은 마우스(또는 터치패드)로 놓습니다. 키보드로는 컨트롤을 고르고(Tab, Shift+Tab), 선택한 컨트롤을 옮기고, 크기를 바꾸고, 지우고, 순서를 바꿀 수 있고, 속성 창에서 컨트롤을 고르고 값을 칠 수 있습니다. 웹에서 Flutter의 접근성 층을 켜면(화면 읽기 프로그램이 켜는 것과 같음) Chrome에서 시험했을 때 도구상자를 더블클릭해도 컨트롤이 놓이지 않았습니다. 도구를 고르고 폼 위를 클릭하는 방법은 됩니다. 원인은 아직 살펴보지 않았습니다.
- **왜 미뤘나:** 디자이너는 폼을 그리는 도구이고, 키보드로 하는 방법은 단계마다 더해집니다.
- **다시 볼 때:** 화면 읽기 프로그램으로 디자이너를 확인할 때(E2d 다음). 키보드로 컨트롤을 놓으려면 도구상자가 포커스를 받아야 합니다.

## 코드가 바뀐 뒤 이름 바꾸기를 실행 취소하면 새 이름이 모두 되돌아갑니다

- **무엇:** 컨트롤 이름을 바꾸면 코드에서도 바뀝니다(D39). 그 뒤 코드를 고치고 이름 바꾸기를 실행 취소하면, 코드 안의 새 이름은 이름을 바꾼 뒤에 쓴 것까지 모두 옛 이름으로 돌아갑니다. 그사이 코드에서 옛 이름을 다른 것(예: 변수)에 썼다면 두 개가 한 이름을 쓰게 되고, 분석기가 이를 알려 줍니다.
- **왜 미뤘나:** 이름을 바꾼 뒤의 코드는 사용자가 쓴 것이므로, 바꾸기 전 텍스트를 되돌리면 그 변경이 사라집니다. 새로 쓴 이름 가운데 어느 것이 컨트롤을 뜻했는지도 알 수 없습니다. 흔한 경우인, 이름을 바꾼 직후의 실행 취소는 코드를 정확히 되돌립니다.
- **다시 볼 때:** 코드 편집기에서 이름 바꾸기(리팩터링)를 할 때. 무엇이 바뀌는지 미리 보여 줄 수 있게 되면.

## 긴 코드 파일에서 칠 때 프레임이 빠질 수 있습니다

- **무엇:** 코드 편집기(D36)는 키를 누를 때마다 코드 파일 전체를 다시 배치합니다. 맥 Release 앱에서 잰 결과, 키 하나 뒤 프레임을 만드는 데 30줄은 10ms까지, 100줄은 4–18ms, 300줄은 8–29ms가 걸렸습니다(처음 몇 키가 가장 느림). 60Hz에서 한 프레임은 16.7ms이고, 300줄 파일에 한 줄을 치는 동안 27프레임 가운데 2개가 빠졌습니다. Chrome에서는 80프레임 가운데 하나가 20ms를 넘었습니다.
- **자동완성 목록과 함께(D50):** 맥 Profile 빌드에서 앱 안에서(integration_test, 운영체제의 키보드 이벤트 없음) 300줄 파일에 한 줄을 치며 잰 결과, 키 하나 뒤 프레임은 중앙값 8.4ms, 90백분위 9.4ms였습니다. 목록을 더하기 전의 빌드는 8.3ms와 9.0ms였고, 두 경우 모두 시간을 넘긴 프레임은 없었습니다. 소프트웨어로 그리는 headless Chrome에서는 목록이 있든 없든 키 하나 뒤 프레임이 20–34ms이고, 처음 그리는 목록 하나가 50–100ms짜리 프레임 하나를 만듭니다(새 목록을 그리는 시간). 그다음 목록은 다른 키와 같습니다. 목록을 찾는 데는 약 40µs가 걸리고, 목록에 쓰는 컴파일은 입력이 멈출 때만 합니다.
- **왜 미뤘나:** Flutter의 글자 칸은 글자 전체를 배치하는데, 300줄이면 색이 칠해진 조각이 1,000개쯤 됩니다. 키마다 프로젝트를 컴파일하고 줄마다 폭을 재던 것을 없애 시간을 절반으로 줄였습니다. 1단계에서 쓰는 프로그램은 수십 줄입니다.
- **다시 볼 때:** 사용자가 150줄쯤 넘는 프로그램을 쓰게 될 때, 또는 자동완성 목록의 첫 프레임이 실제 컴퓨터에서 눈에 띌 때. 그때 화면에 보이는 줄만 배치합니다.

## macOS 앱에서는 조합 중인 음절에 밑줄이 없습니다

- **무엇:** macOS 데스크톱 앱에서 TextBox, 속성 창, 코드 편집기에 한글을 칠 때 조합 중인 음절에 밑줄이 없습니다. 마지막 음절은 다음 음절이 시작되거나, 한글이 아닌 키가 오거나, 칸이 확정할 때(Enter, 클릭, 포커스 이동)에야 프로그램(또는 폼 파일)에 닿습니다.
- **왜 미뤘나:** macOS 27의 한글 입력기는 네이티브 텍스트 칸에 조합 범위를 보내지 않습니다. 텍스트 편집기(TextEdit)에서도 밑줄이 없고, 같은 맥의 Chrome에는 있습니다(DESIGN D37). runtime이 조합을 짐작해서 이벤트는 웹과 같게 나오지만, 밑줄을 그리려면 입력기가 보내지 않는 범위가 필요합니다.
- **다시 볼 때:** macOS 업데이트나 Flutter가 데스크톱 앱에 조합 범위를 보내게 될 때. 그때는 짐작이 저절로 멈추고(범위가 한 번도 오지 않은 동안만 씀), `test/ime_logs/macos-app.json`을 다시 기록합니다.

## 입력기 기록에 음절을 확정하는 Enter가 없습니다

- **무엇:** 블록 완성(DESIGN D50)은 조합 중인 한글을 확정하는 Enter에서는 블록을 닫지 않습니다. 편집기는 그 Enter를 줄바꿈 직전의 조합 상태로, 그리고 확정과 줄바꿈이 두 번에 나뉘어 올 때는 그 사이에 눌린 키가 없다는 것으로 가립니다. `packages/gubasic_runtime/test/ime_logs`의 기록에는 Enter가 없어서, 테스트는 기록을 마지막으로 조합 중인 순간까지 재생한 뒤 브라우저처럼(키, 확정, 줄바꿈) 그리고 맥 앱처럼(줄바꿈만) Enter를 보냅니다. 이 순서는 실제 입력기에서 기록한 것이 아닙니다.
- **왜 미뤘나:** 새 기록에는 컴퓨터마다 작성자의 키보드가 필요합니다(CLAUDE.md). 또 맥 앱에서는 편집기의 추측(D37)이 다른 입력이 올 때까지 마지막 음절을 조합 중으로 보므로, 조합 상태만으로도 가려집니다.
- **다시 볼 때:** 다음에 `ime_probe`로 기록할 때. 음절을 Enter로 끝내는 장면을 macOS(Chrome과 앱)와 Windows(Chrome과 앱)에서 더합니다.

## 데스크톱 IDE에는 최근 프로젝트 목록이 없습니다

- **무엇:** 웹에서는 IDE가 예제로 시작하고 브라우저에 보관된 프로젝트가 있으면, 띠가 그렇다고 알리고 목록을 엽니다(DESIGN D74). 데스크톱 IDE는 마지막에 연 프로젝트를 열지만(D62) 다른 프로젝트의 목록은 기억하지 않습니다. 파일 → 열기로 찾아가야 합니다.
- **왜 미뤘나:** 웹은 이미 자기 프로젝트를 알고 있습니다. 데스크톱은 설정과 함께 폴더 목록을 기억해야 하고, 없어진 폴더를 지울 방법도 있어야 합니다.
- **다시 볼 때:** 사용자가 데스크톱 IDE에서 여러 프로젝트를 오가며 쓸 때, 또는 메뉴에 파일 → 최근 항목을 넣을 때.

## 내보낸 Windows 앱의 파일 정보는 GuBASIC Player라고 합니다

- **무엇:** 내보낸 Windows 앱의 프로그램 이름은 프로젝트 이름으로 바뀌고 창 제목도 프로젝트 이름이지만(D86), 작업 관리자가 이름으로 보여 주는 프로그램의 파일 정보는 여전히 "GuBASIC Player"이고 GuBASIC의 버전과 저작권 표시를 담습니다. 또 SaveSetting은 내보낸 모든 앱의 값을 사용자의 AppData 폴더 안, 같은 "GuBASIC Player" 이름의 파일 하나에 앱 ID별로 나누어 둡니다.
- **왜 미뤘나:** 바꾸려면 프로그램의 버전 리소스를 고쳐 써야 하는데, IDE는 아직 그 일을 하지 않습니다. 앱 ID가 이미 앱마다 설정을 나눕니다.
- **다시 볼 때:** 같은 리소스를 고쳐 쓰는 앱 아이콘 고르기(STAGE2_PLAN §9) 때.

## 내보낸 macOS 앱의 프로그램 이름은 GuBASIC Player입니다

- **무엇:** 내보낸 macOS 앱은 Finder, Dock, 메뉴, 강제 종료 창에서 프로젝트 이름으로 보이지만(D87), 앱 안의 프로그램(`Contents/MacOS`)은 `GuBASIC Player`라는 이름을 그대로 가지며, `ps`와 충돌 보고서에는 이 이름이 나옵니다. 또 앱은 틀의 `get-task-allow` 권한을 그대로 가져서 디버거가 붙을 수 있습니다.
- **왜 미뤘나:** `codesign`은 프로그램 이름이 ASCII가 아닌 앱을 확인하지 못합니다. 영어 이름 프로젝트만 프로그램 이름을 바꾸면 한글 프로젝트와 달라집니다. 권한을 빼려면 내보낼 때마다 권한을 새로 써야 합니다.
- **다시 볼 때:** 내보내기가 앱의 정보를 더 많이 쓰게 되는 앱 아이콘 고르기(STAGE2_PLAN §9) 때.

## 프로젝트의 폼은 창 하나를 함께 씁니다

- **무엇:** `Form2.Show`는 Form1과 같은 창, 또는 페이지에 Form2를 보이며 Form1을 가립니다(D88, D89). 데스크톱에서는 창이 Form2의 크기가 됩니다. Visual Basic과 2-7 단계 전의 계획(DESIGN §3.3)은 데스크톱에서 폼마다 창을 열었습니다.
- **왜 미뤘나:** GuBASIC이 고정해 쓰는 Flutter 3.47.7에는 창 여러 개를 위한 클래스가 깃발 뒤의 내부용으로만 있습니다. 창마다 엔진을 띄우면 폼끼리 변수를 나눠 쓸 수 없습니다.
- **다시 볼 때:** Flutter의 다중 창 API가 공개될 때.

## 대화상자 폼에는 닫기 단추가 없습니다

- **무엇:** `ShowDialog`로 띄운 폼은 뒤의 폼 위에 자체 닫기 단추 없이 그려집니다(D89). 그 코드의 `Me.Hide`나 `Me.Close`만 대화상자를 치웁니다. 코드가 그러지 않으면 대화상자는 창을 닫을 때까지 남고, 창을 닫으면 프로그램이 끝납니다.
- **왜 미뤘나:** 대화상자의 닫기 단추가 무엇을 할지 규칙이 필요합니다. Visual Basic .NET은 `DialogResult`와 함께 취소로 다루는데, `DialogResult`는 나중입니다(D90).
- **다시 볼 때:** `DialogResult`를 넣을 때.

## 폼 닫기를 취소할 수 없습니다

- **무엇:** `Form_Closed`는 폼이 닫힌 뒤, 또는 창을 닫아 프로그램이 끝나기 전에 돕니다(D88). Visual Basic 6의 `QueryUnload`나 .NET의 `FormClosing`처럼 Cancel 인자로 폼을 열어 두게 하는 이벤트는 없습니다.
- **왜 미뤘나:** Cancel 인자는 `ByRef` 매개변수인데, `ByRef`는 2단계 뒤쪽에 옵니다.
- **다시 볼 때:** `ByRef`를 넣을 때.
