# 알려진 문제

[English](KNOWN_ISSUES.md)

알고 있지만 지금은 **일부러** 고치지 않은 문제를 적어 둡니다. 항목마다 무엇인지, 왜 미뤘는지, 언제 다시 볼지를 적습니다. 문제를 고치면 같은 변경에서 항목을 지웁니다.

---

## 아주 긴 반복이 느림

- **무엇:** 100만 번 도는 반복(`total = total + i * 2 - 1`)이 놀이터의 웹 최적화 빌드에서 약 3초, VM에서 약 0.8초 걸립니다.
- **왜 미뤘나:** 정확성 문제가 아니고, 초보자가 쓰는 프로그램 규모에서는 체감되지 않습니다.
- **다시 볼 때:** 놀이터나 IDE에서 실제로 느리다는 사례가 생길 때, 또는 트랜스파일러 단계.

## 설정 기능을 아직 쓸 수 없음

- **무엇:** `SaveSetting`과 `GetSetting`은 실행 전에 진단하며(A029) 쓸 수 없습니다.
- **왜 미뤘나:** 설정을 저장하는 곳이 플랫폼마다 다릅니다(앱은 shared_preferences, 놀이터는 브라우저 저장소). 인터프리터와 생성된 앱이 같은 방식으로 저장하도록 `gubasic_runtime`과 함께 만들어야 합니다(D11).
- **다시 볼 때:** `gubasic_runtime`이 생길 때.

## 놀이터는 폼을 실행하지 않음

- **무엇:** 폼은 IDE의 실행 창(`apps/ide`)과 동일성 테스트에서 실행되지만, 놀이터는 폼이 없는 프로그램만 실행합니다. 놀이터에서는 여전히 컨트롤과 `Me`를 알립니다(A003).
- **왜 미뤘나:** 놀이터는 Flutter 없는 순수 Dart이고, HTML로 컨트롤을 흉내 내면 두 번째 런타임이 생깁니다(D24). 브라우저에서는 대신 IDE의 웹 빌드(E1e)가 폼을 실행합니다.
- **다시 볼 때:** IDE의 웹 빌드를 게시할 때. 그때 놀이터에 실행 탭이 여전히 필요한지 정합니다.

## IDE가 마지막 프로젝트를 다시 열지 않음

- **무엇:** 데스크톱 IDE는 늘 `hello` 예제로 시작합니다. 프로젝트는 그때마다 파일 → 열기…로 다시 열어야 합니다.
- **왜 미뤘나:** 프로젝트를 기억하는 것(마지막 프로젝트, 또는 최근 프로젝트 목록)은 따로 만들 기능입니다: 목록을 어디에 둘지, 프로젝트를 옮기거나 지웠을 때 어떻게 할지 정해야 합니다. 프로젝트를 여는 데는 대화상자 하나면 됩니다.
- **다시 볼 때:** 최근 프로젝트 목록을 만들 때, 또는 학생들이 다시 여는 것을 번거로워할 때.

## 웹 IDE가 브라우저에 보관한 프로젝트는 사라질 수 있음

- **무엇:** 웹에서는 프로젝트를 브라우저의 `localStorage`에 보관합니다(D33). 브라우저 데이터를 지우면 함께 사라지고, 공용 PC는 로그아웃할 때마다 지울 수 있으며, Safari는 7일 동안 방문하지 않으면 지웁니다. 같은 프로젝트를 탭 두 개에서 열면 마지막에 저장한 쪽이 남습니다.
- **왜 미뤘나:** 웹 페이지는 스스로 디스크에 파일을 보관할 수 없습니다. IDE는 `.zip` 내려받기를 한 번에 누를 수 있게 두고, 내려받지 않은 변경이 있는 동안 내려받으라고 알리며, 처음 저장할 때 이 점을 알립니다.
- **다시 볼 때:** 학생들이 실제로 작업을 잃을 때. 그때 브라우저가 허용하는 곳에서는 폴더에 저장하는 방법(File System Access API, Chrome과 Edge만)을 검토합니다.

## 브라우저 저장소는 그림을 담기에 작음

- **무엇:** `localStorage`는 사이트마다 약 5MB입니다. 지금 프로젝트는 몇 KB의 텍스트지만, 폼에 그림을 넣을 수 있게 되면(`Image` 컨트롤, 1단계) 프로젝트 몇 개로 가득 찹니다.
- **왜 미뤘나:** 아직 그림을 보관하는 것이 없고, `localStorage`는 동기식이라 페이지가 닫히는 중에도 프로젝트가 보관됩니다.
- **다시 볼 때:** `Image` 컨트롤을 만들 때. 브라우저의 프로젝트를 IndexedDB(또는 더 큰 저장소)로 옮기고, 이미 보관된 것을 옮기는 변환기를 둡니다.

## 실행 창이 IDE 창 안에 있음

- **무엇:** 실행 중인 프로그램의 폼은 따로 된 창이 아니라 IDE 창 가운데에 나타납니다. 폼을 옮기거나 프로그램 둘을 나란히 실행할 수 없습니다.
- **왜 미뤘나:** 창 하나로 하면 데스크톱과 웹에서 똑같이 동작합니다. 창을 따로 띄우려면 데스크톱 운영 체제마다 플랫폼 코드가 필요합니다.
- **다시 볼 때:** 폼 디자이너와 함께 IDE의 창 배치를 정할 때.

## 한글 입력은 아직 Chrome에서만 시험함

- **무엇:** TextBox 테스트는 Chrome에서 Windows 한글 입력기와 macOS 한글 입력기(두벌식)가 보낸 신호를 재생합니다(`packages/gubasic_runtime/test/ime_logs/`). 데스크톱 앱은 아직 실제 입력기로 시험하지 않았습니다. macOS는 IDE 실행 창과 함께 시험합니다. Windows는 빌드하려면 Visual Studio가 필요한데, 결정에 따라 Windows PC에 설치하지 않았습니다.
- **두 기록에서 본 것:** 둘 다 LANGUAGE 11.1절의 약속을 지킵니다. 다섯 시나리오 모두에서 같은 이벤트를 만들었습니다. 스페이스는 앞 음절과 함께 확정되므로, 닭 다음에 `Changed`는 `닭 `은 보지만 `닭`만 따로는 보지 않습니다. 도중의 신호만 다릅니다(macOS는 스페이스를 먼저 조합 안에 넣습니다). 둘 다 입력 칸이 포커스를 잃을 때 조합 중인 글자를 확정하며, 웹에서는 클릭보다 150~180 ms쯤 먼저입니다.
- **그때 확인할 Flutter 문제:** Windows 데스크톱에서 빠르게 치면 음절이 빠지는 문제([flutter/flutter#189491](https://github.com/flutter/flutter/issues/189491), 열림). 웹에서 브라우저가 조합을 버리면 조합 범위가 남는 문제([flutter/flutter#193847](https://github.com/flutter/flutter/issues/193847))는 Flutter master에서 고쳤지만 3.47.7에는 없습니다. 두 Chrome 기록 모두에서 생기지 않았습니다. 입력 칸을 떠날 때 글자가 깨끗하게 확정되었습니다.
- **왜 미뤘나:** 기록하려면 사람이 시스템마다 직접 쳐야 하고, Visual Studio는 웹에는 필요 없는 큰 설치입니다.
- **다시 볼 때:** IDE 실행 창을 macOS 데스크톱에서 돌릴 때(E1d), 그리고 Windows PC에 Visual Studio를 설치할 때.

## 나중에 만든 앱에서 IDE에서 그린 글자가 잘릴 수 있음

- **무엇:** 런타임은 글꼴을 고르지 않으므로(DESIGN 2.3절), 나중에 트랜스파일러로 만든 앱은 기기의 기본 글꼴을 씁니다. IDE는 담아 온 Noto Sans KR을 씁니다(D30). 그러면 출시된 앱의 글자 폭이 IDE와 달라져, 맞게 그린 Label의 글자가 잘릴 수 있습니다.
- **왜 미뤘나:** 트랜스파일러가 아직 없습니다.
- **다시 볼 때:** 트랜스파일러 단계. 선택지로는 생성 앱에도 같은 글꼴을 넣는 것(약 9 MB 커짐), 디자이너가 글자 잘림 위험을 경고하는 것 등이 있습니다.

## 웹 IDE의 글꼴 불러오기는 로컬 서버로만 확인함

- **무엇:** 외부 주소를 모두 막고(headless Chrome, `--host-resolver-rules="MAP * ~NOTFOUND, EXCLUDE 127.0.0.1"`, 웹 빌드를 로컬 서버로 띄움) 열었을 때, IDE의 한국어 문구가 바르게 나오고 페이지가 외부에서 받는 것이 없었습니다. 엔진, 글꼴, 대체 글꼴 모두 로컬 서버에서 왔습니다. macOS와 Windows(Chrome 155)에서 확인했습니다. 넷 로그에 남은 외부 요청은 업데이트, 맞춤법 사전처럼 Chrome이 스스로 보낸 것뿐이었습니다. 음절이 □로 빠지는 문제([flutter/flutter#188255](https://github.com/flutter/flutter/issues/188255))는 나타나지 않았습니다.
- **느린 네트워크에서 첫 방문**(Windows, headless Chrome, 캐시 끔, DevTools의 Slow 4G 설정: 지연 562.5 ms, 180 kB/s, 127.0.0.1에서 받음): "불러오는 중…"이 1.1초부터 약 102초의 첫 화면까지 보였습니다. Noto Sans KR 두 파일이 100.3초와 101.3초에 도착했고, 첫 화면은 그 바로 뒤에 그려졌습니다. 모든 프레임을 화면 녹화(screencast)로 보니 불러오는 중 문구에서 Noto Sans KR로 다 그려진 IDE로 바로 넘어갔습니다. 다른 글꼴로 그린 프레임이 없었으므로, 처음에 다른 글꼴로 그렸다가 바로잡히는 문제([flutter/flutter#77023](https://github.com/flutter/flutter/issues/77023))는 나타나지 않았습니다. `typing`을 실행하고 TextBox에 동해물과 백두산이 닭 값을 넣었을 때 TextBox와 Label 모두 □ 없이 나왔습니다.
- **왜 미뤘나:** 모두 127.0.0.1에서 받았으므로 실제 네트워크(학교망 등)를 거치지 않았습니다. 그러려면 Pages 배포(E1e)가 필요합니다.
- **다시 볼 때:** Pages 배포(E1e) 뒤, 학교 PC의 보통 브라우저로 실제 주소를 열어 학교망에서 열리는지 확인하고 첫 방문에 걸리는 시간을 잽니다.

## 웹에서는 코드 보기가 고정폭이 아님

- **무엇:** IDE의 코드 보기와 출력은 `monospace` 글꼴을 요청하지만 웹 빌드에는 그 글꼴이 없어서, 웹에서는 코드가 비례폭 글꼴로 보입니다(그 안의 한글은 Noto Sans KR).
- **왜 미뤘나:** 고정폭 글꼴을 넣으면 내려받을 크기가 늘어나고(D30), 코드 편집기가 생기기 전까지 코드 보기는 읽기 전용입니다.
- **다시 볼 때:** 코드 편집기(ROADMAP)와 함께. 코드 글꼴은 편집기에서 정합니다.

## 폼 디자이너에서 복사와 붙여넣기가 안 됩니다

- **무엇:** 폼 디자이너에서 컨트롤을 복사하거나 잘라 내거나 붙여 넣을 수 없습니다(⌘C / ⌘X / ⌘V, Ctrl+C / Ctrl+X / Ctrl+V).
- **왜 미뤘나:** 붙여 넣은 컨트롤에는 새 이름과 자리가 필요하고, 무엇을 복사할지는 속성 창(E2d)이 정하는 속성에 달려 있습니다. 새 컨트롤은 한 번 끌어서 그릴 수 있습니다.
- **다시 볼 때:** E2d(속성 창) 다음에.

## 폼 디자이너는 컨트롤을 하나씩만 선택하고, 그린 순서를 바꿀 수 없습니다

- **무엇:** 컨트롤을 하나만 선택할 수 있어서 여러 개를 함께 옮기거나 지울 수 없습니다. 새 컨트롤은 늘 다른 컨트롤 위에 그려지고, 순서를 바꿀 수 없습니다("맨 앞으로", "맨 뒤로" 없음).
- **왜 미뤘나:** 1단계의 폼에는 겹치지 않는 컨트롤 몇 개가 있을 뿐이고, 여러 개를 함께 선택하면 옮기기와 크기 조절에 따로 규칙이 필요합니다.
- **다시 볼 때:** 컨트롤이 많은 폼(ListBox, Image, 1단계)에서 불편해질 때, 또는 `Anchor`와 함께.

## 폼 디자이너는 마우스가 있어야 합니다

- **무엇:** 컨트롤은 마우스(또는 터치패드)로 놓고 선택합니다. 키보드로는 선택한 컨트롤을 옮기고, 크기를 바꾸고, 지우고, 되돌리고, 포인터로 돌아갈 수 있습니다. 웹에서 Flutter의 접근성 층을 켜면(화면 읽기 프로그램이 켜는 것과 같음) Chrome에서 시험했을 때 도구상자를 더블클릭해도 컨트롤이 놓이지 않았습니다. 도구를 고르고 폼 위를 클릭하는 방법은 됩니다. 원인은 아직 살펴보지 않았습니다.
- **왜 미뤘나:** 디자이너는 폼을 그리는 도구이고, 키보드로 하는 방법은 단계마다 더해집니다.
- **다시 볼 때:** 값을 입력할 수 있는 속성 창(E2d)과 함께. 그때 화면 읽기 프로그램으로 디자이너를 확인합니다.
