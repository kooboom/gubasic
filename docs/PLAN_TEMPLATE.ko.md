# 계획서 양식

[English](PLAN_TEMPLATE.md)

기능이나 변경의 계획서는 모두 이 모양으로 써서, 작업을 시작하기 전에 작성자에게 보입니다. 빼는 절은 왜 빼는지 적습니다.

## 1. 무엇을, 왜

- 사용자가 무엇을 할 수 있게 되는지 한두 문장으로, 가장 작은 예제 프로그램과 함께.
- [로드맵](ROADMAP.ko.md)의 어느 단계인지, 기대는 결정(D 번호)은 무엇인지.

## 2. 쓰는 모습

- 사용자가 쓸 문법이나 컨트롤, 그리고 다른 BASIC은 같은 것을 무엇이라 부르는지(GuBASIC의 이름을 알려 주는 진단을 위해, D50).
- 메시지: 새 진단을 영어와 한국어로.

## 3. 설계

- 어디에 들어가나: `gubasic_lang`, `gubasic_runtime`, `gubasic_player`, 앱. 새 파일.
- 무엇을 열어 두나: 트랜스파일러(AST 하나), 프로젝트 형식(`formatVersion`), CLAUDE.md의 하드 규칙.

## 4. 둘러가지 않기(D121)

하나씩 답합니다.

- **사용자가 우회해야 하는 곳이 남는가?** 저수준 코드로 흉내 내야 하는 것, 게시판에서 배워야 하는 편법, 보통의 방식을 막는 한계가 있는가. 있다면 무엇을 대신 기본으로 주는지, 아니면 왜 나중으로 미루는지(그러면 KNOWN_ISSUES에 적음).
- **바깥과 표준으로 이야기하는가**(HTTP, JSON, WebSocket, CSV, SQLite, UTF-8)? 표준의 출처와 함께.
- **스스로 하지 않는 일을 받아들일 통로가 있는가**(컴포넌트 통로, [COMPONENT_CHANNEL.ko.md](COMPONENT_CHANNEL.ko.md))?
- **문서와 예제:** LANGUAGE의 어느 절이 바뀌는지, 어느 예제가 보여 주는지, AI용 참조(`llms.txt`)에 무엇이 들어가는지.

## 5. 테스트

- 동일성 프로그램(`test/parity/`): VM, Chrome, 실행 창.
- 위젯·통합 테스트, 그리고 손으로 확인하는 것(웹은 Playwright로, 맥은 작성자의 마우스와 키보드를 쓰지 않는 방법으로만).

## 6. 작성자에게 물을 것

각각 권장안과 함께.
