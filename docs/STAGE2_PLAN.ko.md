# 2단계 계획 — 진짜 앱 만들기

[English](STAGE2_PLAN.md)

**상태: 작성자가 2026-10-26에 §6의 결정과 함께 승인했습니다. 2-0부터 2-2까지 먼저 하고, 2-2가 끝나면 작성자가 그 측정 결과(§7)와 묶음 설계안(2-3 단계)을 보고 다음 단계를 정합니다.**

이 계획은 GuBASIC 프로젝트를 IDE 없이 혼자 도는 앱(웹, macOS, Windows)으로 만드는 방법을 다룹니다. 세 가지 방식을 비교하고, 사용자 컴퓨터에 Flutter가 없을 때 빌드를 어디서 하는지 정하고, 일을 작은 단계로 나눕니다. 단계마다 끝나면 직접 볼 수 있는 것이 있습니다.

**지금까지 효력이 있던 문서를 바꾸므로**, 몰래 벗어나지 않고 여기에 밝힙니다(CLAUDE.md). 2-0 단계에서 먼저 아래 문서를 고칩니다.

- DESIGN §2.2와 D3은 트랜스파일러를 출시하는 *유일한* 길로 설명합니다. §2.3에는 "생성된 앱에는 인터프리터를 넣지 않는다"는 문장이 있고, §12에는 첫 빌드 때 Flutter를 내려받는다고 되어 있습니다.
- ROADMAP 2단계는 트랜스파일러를 맨 앞에 두고, "한 프로젝트를 네 플랫폼(Android 포함)에 출시하면" 끝난다고 되어 있습니다.
- CLAUDE.md는 네이티브 출시 빌드를 트랜스파일러로 만든다고 설명하고, 하드 규칙 3은 "두 모드"의 패리티를 요구합니다.

하드 규칙 자체는 그대로 둡니다. 모든 실행 방식이 AST 하나를 쓰고(규칙 2), 모든 기능에 패리티 테스트가 있고(규칙 3), 인터프리터는 비동기이고(규칙 4), 앱은 `gubasic_runtime`으로만 그립니다(규칙 6). 이 규칙을 지켜야 나중에 트랜스파일러를 넣을 길이 열려 있습니다.

## 1. 목표

IDE에서 앱을 만든 학생이 그 앱을 다음 가운데 하나로 만들 수 있게 합니다.

- **웹 앱:** 어느 웹 호스트에 올려도 브라우저에서 도는 파일 폴더
- **macOS 앱**과 **Windows 앱:** GuBASIC도 Flutter도 없는 컴퓨터에서 두 번 눌러 여는 앱

앱은 IDE에서 F5로 실행했을 때와 똑같이 보이고 똑같이 동작합니다. 같은 `gubasic_runtime` 위젯으로 폼을 그리고(규칙 6), 같은 실행 모델(한 번에 처리기 하나, 모달 대화상자, `DoEvents`, DESIGN §3)을 따르기 때문입니다.

쓰는 사람은 초등학생과 교사입니다. 아래 선택은 대부분 이 점으로 정했습니다: 설치할 개발 도구도, 만들 계정도, 명령줄도 없어야 합니다.

## 2. 세 가지 방식

### (가) 트랜스파일러: BASIC → Dart → `flutter build`

IDE가 프로젝트의 코드를 Dart로 바꾸고, 그 둘레에 Flutter 프로젝트를 쓰고, Flutter가 컴파일합니다.

- **장점:** 가장 빠른 앱입니다(AOT 네이티브 코드라, KNOWN_ISSUES에 적은 인터프리터의 긴 반복이 느린 문제가 사라짐). 앱에 인터프리터가 들어가지 않습니다. 장기 설계(D3)가 이미 이 방식이고, pub.dev 추가 컴포넌트(DESIGN §5.1)와 Dart 직접 넣기(3단계)도 이 방식이 있어야 합니다.
- **단점:** 누군가는 Flutter를 돌려야 합니다. macOS 앱에는 Xcode가, Windows 앱에는 Visual Studio의 "Desktop development with C++"가 필요합니다([Flutter: macOS 설정](https://docs.flutter.dev/platform-integration/macos/setup), [Flutter: Windows 설정](https://docs.flutter.dev/platform-integration/windows/setup)). 수 기가바이트에 이르고, 학교 PC나 어린이가 설치할 것이 아닙니다. 또 생성한 코드가 인터프리터의 동작을 문장 하나하나까지 똑같이 재현해야 합니다: 모든 프로시저의 비동기, 한 번에 처리기 하나, 재진입 막기, `DoEvents`, 코드와 줄 번호가 붙은 실행 중 오류.
- **패리티:** `test/parity/`의 모든 프로그램을 두 방식으로 돌려 기록을 비교합니다. 폼이 없는 프로그램은 `dart run`으로 돌릴 수 있지만, 폼이 있는 프로그램은 CI에서 생성된 프로젝트로 `flutter test`를 돌려야 합니다.
- **오류 메시지와 줄 번호:** Dart 예외는 `.gbas`의 줄을 모릅니다. 생성된 코드가 줄 번호를 실행 도우미에 넘기고, 도우미가 GuBASIC 자체의 오류(R0xx, 한국어·영어 메시지)를 내야 합니다. Dart가 던질 수 있는 모든 예외를 잡아서 바꿔야 합니다.
- **앱 크기:** 셋 가운데 가장 작습니다.
- **노력:** 가장 큽니다. AST 전체를 위한 코드 생성기, 실행 모델의 두 번째 구현, 빌드 파이프라인, CI에서 Flutter를 돌리는 패리티 시설이 모두 필요합니다.

### (나) 플레이어: 인터프리터와 프로젝트를 미리 만든 앱에 넣기

**플레이어**는 GuBASIC의 CI가 한 번 빌드해 두는 Flutter 앱입니다. 인터프리터(`gubasic_lang`)와 실행 창이 들어 있고, 주어진 프로젝트를 실행합니다. 학생의 앱을 "빌드"한다는 것은 플레이어를 복사해 프로젝트 파일을 넣는 일이라 컴파일러가 전혀 필요 없습니다.

- **장점:** 어디에도 Flutter가 없어도, 웹 IDE에서도 됩니다. F5와 같은 인터프리터 코드, 같은 실행 창 코드를 쓰므로 패리티가 구조적으로 지켜집니다. 같은 플레이어가 3단계의 폰용 플레이어가 됩니다(DESIGN §12).
- **단점:**
  - 인터프리터의 속도입니다. 웹에서 백만 번 도는 반복이 3초쯤 걸립니다(KNOWN_ISSUES).
  - 앱에 인터프리터와 소스 코드가 들어가 누구나 읽을 수 있습니다. 앱에 넣은 것은 모두 꺼낼 수 있다는 것은 DESIGN §11이 이미 전제한 점입니다.
  - macOS 앱의 파일을 바꾸면 서명이 깨집니다. Apple Silicon에서는 모든 실행 파일이 서명되어 있어야 실행되고, ad-hoc 서명으로도 충분합니다([Apple: macOS Big Sur 11.0.1 유니버설 앱 릴리스 노트](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes), [The Eclectic Light Company의 인용](https://eclecticlight.co/2020/08/22/apple-silicon-macs-will-require-signed-code/)). 그래서 프로젝트를 넣은 뒤 macOS 앱을 다시 서명해야 합니다.
- **패리티:** IDE의 실행 창과 플레이어가 패키지 하나를 함께 쓰므로(2-1 단계) 시험할 구현이 하나입니다. 지금 있는 패리티 프로그램과 이벤트 스크립트(DESIGN §9.1)를, 지금 IDE로 돌리듯 위젯 테스트에서 플레이어로도 돌립니다.
- **오류 메시지와 줄 번호:** 인터프리터와 똑같습니다. 같은 R0xx 코드, 한국어·영어 메시지, `.gbas` 줄 번호입니다.
- **앱 크기:** Flutter 앱 자체의 크기에 인터프리터, 런타임, 프로젝트가 더해진 정도입니다. 2-1 단계에서 잽니다. 비교하면, IDE 전체가 macOS에서 51MB이고 웹 빌드의 코드(`main.dart.js`)가 3.3MB입니다.
- **노력:** 중간입니다. 작은 앱 하나, 프로젝트 묶음 형식, 내보내기 명령, 미리 만든 플레이어를 릴리스마다 함께 내놓는 방법, macOS 다시 서명이 필요합니다.

### (다) 둘 다, 차례로: 지금은 플레이어, 트랜스파일러는 나중

2단계는 플레이어(나)로 앱을 내보냅니다. 트랜스파일러(가)는 설계상의 장기적인 빠른 길로 남기고, 필요해질 때 다시 계획합니다. 필요해지는 때는 플레이어로는 너무 느린 프로그램, 추가 컴포넌트, Dart 직접 넣기입니다. 셋 다 트랜스파일러가 있어야 합니다.

**결정: (다).** Visual Basic 6도 같은 방식으로 앱을 내놓았습니다. 모든 프로그램이 폼, 컨트롤, 실행 함수를 위해 런타임 DLL인 MSVBVM60.DLL을 썼고, p-code로 컴파일하면 런타임이 실행하면서 문장 하나하나를 네이티브 코드로 바꿨습니다. Professional과 Enterprise 판에서는 네이티브 코드로도 컴파일할 수 있었지만, 그때도 DLL은 필요했습니다([Microsoft: Compiling your project to native code](https://learn.microsoft.com/en-us/previous-versions/visualstudio/visual-basic-6/aa240843(v=vs.60))). GuBASIC의 플레이어는 p-code 자리에 인터프리터가 들어간 그 런타임이고, 트랜스파일러는 나중의 네이티브 코드 선택지입니다. GuBASIC을 쓰는 사람에게 맞는 것은 (나)뿐입니다. Flutter, Xcode, Visual Studio, 명령줄이 모두 필요 없고, 1단계에서 만들고 시험한 것을 그대로 다시 씁니다. (가)를 버리는 것은 아닙니다. AST는 계속 함께 쓰고(규칙 2), 플레이어를 위해 쓴 패리티 프로그램이 나중에 트랜스파일러가 통과해야 할 프로그램이 됩니다.

## 3. 빌드는 어디서 하나

사용자 컴퓨터에는 Flutter가 없습니다. 남는 길은 다음과 같습니다.

| 길 | 웹 | macOS | Windows | 어린이와 교사에게 |
|---|---|---|---|---|
| **플레이어 틀**(나): GuBASIC CI가 릴리스마다 플레이어를 빌드하고, IDE가 프로젝트를 넣음 | IDE가 웹 플레이어와 프로젝트를 zip으로 묶음. 브라우저 안에서도 됨 | macOS IDE가 프로젝트를 넣고 앱을 다시 서명함(시스템의 `codesign`으로 ad-hoc) | 어느 IDE든 실행 파일 옆에 프로젝트 폴더를 넣음 | 도구도 계정도 필요 없음. 틀을 한 번 받으면 오프라인에서도 됨 |
| IDE가 Flutter를 내려받음(가) | 가능 | Xcode도 필요 | Visual Studio도 필요 | 너무 크고 어려움 |
| GitHub Actions 클라우드 빌드(가) | 됨 | 됨 | 됨 | GitHub 계정이 필요하고, GitHub 약관은 "만 13세 이상이어야 한다"고 정함([GitHub 서비스 약관](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). 학생이 아니라 교사의 길 |
| 브라우저 안에서 Dart 컴파일(가) | 시도하지 않음 | — | — | 컴파일러가 페이지 안에서 돌아야 함. 범위 밖 |

**결정:** 플레이어 틀. IDE에는 틀을 넣지 않습니다(넣으면 웹 IDE가 훨씬 무거워짐). 처음 내보낼 때 자기 버전의 틀을 GuBASIC의 GitHub Release나 Pages에서 받아 보관합니다. macOS 앱은 다시 서명할 수 있는 macOS IDE에서만 내보내고, Windows IDE와 웹 IDE는 웹 앱과 Windows 앱을 내보냅니다.

학생이 보는 것은 다음과 같습니다: **파일 → 앱으로 내보내기…**, 웹·Windows·macOS 가운데 고르기, 폴더나 `.zip`, 여는 방법 몇 줄(macOS는 v0.1.0 릴리스 노트의 단계).

## 4. 여러 폼: 2단계 안에서, 내보내기 다음에

여러 폼(`Form2.Show`, DESIGN §3.3)은 언어와 런타임의 기능입니다. 앱을 내보내든 말든 인터프리터, 실행 창, 디자이너, 프로젝트 파일, 패리티 테스트가 모두 바뀝니다. 내보내기는 여러 폼을 필요로 하지 않고, 프로젝트에 있는 것을 그대로 담습니다.

**결정:** 2단계에 두되, 내보내기 바로 다음의 따로 된 묶음(2-7, 2-8 단계)으로 합니다. 내보내기를 먼저 하면 학생이 집에 가져갈 수 있는 것이 더 빨리 생기고, 묶음마다 따로 검토할 수 있습니다.

## 5. 단계

단계마다 끝나면 작성자가 볼 수 있는 것이 있습니다. 모든 단계는 1단계의 규칙을 지킵니다: 테스트, 패리티, 한국어·영어 메시지, 두 언어의 문서, 확인한 뒤에만 병합하는 PR.

| 단계 | 하는 일 | 끝나면 볼 수 있는 것 |
|---|---|---|
| **2-0** | 아래 결정을 적음: DESIGN(새 D 번호, §2.2·§2.3·§12 수정), ROADMAP 2단계 순서, CLAUDE.md의 출시 빌드 설명 | 문서만 고친 PR |
| **2-1** | 실행 창과 `RunHost`를 `apps/ide`에서 둘이 함께 쓰는 패키지로 옮김(`packages/gubasic_player`, 이름은 정할 것). IDE는 전과 똑같이 동작 | IDE 테스트와 위젯 패리티 테스트가 그대로 통과. F5 화면이 같음 |
| **2-2** | `apps/player`: IDE 없이 프로젝트 하나를 창 가득 실행하는 Flutter 앱. 지금은 프로젝트를 안에 넣어 둠. CI가 웹·macOS·Windows로 빌드하고 크기를 알림. §7의 기준 프로그램 속도를 IDE와 플레이어에서 재고, 트랜스파일러를 다시 볼 숫자를 §7에 적음 | `flutter run`으로 hello가 혼자 도는 앱으로 보임. 세 빌드의 크기. 측정 결과와 기준 |
| **2-3** | 프로젝트 묶음: 프로젝트의 파일과 그림을 파일 하나로 묶음. 첫 판부터 형식 버전(`formatVersion`, 규칙 8)을 넣고, 2-7에서 프로젝트가 여러 폼을 갖기 전부터 여러 폼을 담을 수 있게 설계함. 플레이어가 시작할 때 읽고, 자기가 모르는 새 형식이면 메시지와 함께 거절. 설계안은 2-2가 끝난 뒤 만들기 전에 보고 | 플레이어가 묶음에서 quiz 예제를 엶. 테스트가 모든 예제를 열어 봄 |
| **2-4** | 웹 내보내기: 파일 → 앱으로 내보내기… → 웹. 데스크톱 IDE와 웹 IDE 모두. 틀을 받아 보관 | 풀어서 어느 웹 호스트(GitHub Pages, 학교 서버)에 올려도 앱이 도는 `.zip`. Chromium과 WebKit에서 확인 |
| **2-5** | Windows 내보내기 | 내보낸 폴더가 학교 PC에서 실행됨(작성자가 확인, CI는 파일이 빠짐없는지 확인) |
| **2-6** | macOS 내보내기. macOS IDE에서, ad-hoc으로 다시 서명 | 내보낸 앱이 맥에서 "그래도 열기" 뒤에 열림. `codesign --verify` 통과 |
| **2-7** | 언어와 실행 창의 여러 폼: `Form2.Show`, `Hide`, `Unload`, 시작 폼 또는 `Sub Main`(DESIGN §3.2, §3.3). 패리티 프로그램 포함 | 폼 둘짜리 예제가 F5로도, 내보낸 앱으로도 돎 |
| **2-8** | 디자이너와 프로젝트 파일의 여러 폼 | IDE에서 폼을 더하고, 이름을 바꾸고, 지우기 |
| **2-9** | `Timer` 컨트롤: `Interval`, `Enabled`, `Tick` 이벤트. 패리티 테스트를 위한 이벤트 스크립트 단계 포함 | §7의 작은 게임을 `DoEvents` 반복 대신 Timer로 쓴 것 |
| **2-10** | 키 이벤트: 폼의 `KeyDown`과 `KeyUp`. 이벤트 스크립트 단계 포함 | 화살표 키로 움직이는 도형. F5와 내보낸 앱 모두 |

ROADMAP의 다른 2단계 항목(`LayoutMode`, `Handles`, `OptionButton`, 메뉴, `Database`, `Http`, `ByRef`)은 이 다음에, 하나씩 따로 계획합니다.

**Timer와 키 이벤트: 2단계에, 여러 폼 다음에(2-9, 2-10).** 폼을 작은 게임이나 애니메이션으로 바꾸는 것이 이 둘이고, 아이들이 다음으로 가장 만들고 싶어 하는 것입니다. 둘 다 인터프리터와 플레이어에서 똑같이 돌므로 트랜스파일러가 필요 없습니다. Timer는 다른 컨트롤과 같은 컨트롤이고(`component.yaml`, 규칙 7), 틱은 클릭과 같은 이벤트라 실행 모델을 따릅니다. 다시 들어가지 않고, 처리기가 도는 동안 온 틱은 다른 이벤트처럼 기다립니다(DESIGN §3.1). 키 이벤트는 키보드가 있는 웹과 데스크톱을 위한 것이고, 폰(3단계)에서는 그냥 오지 않습니다.

## 7. 속도: 2-2에서 잴 것과, 트랜스파일러를 다시 볼 때

플레이어는 F5와 같은 인터프리터를 돌리므로 IDE만큼 빠를 것입니다. 2-2 단계는 그렇다고 가정하지 않고 재서, 결과를 숫자로 바꿉니다.

**기준 프로그램.** 각각 IDE(F5)와 플레이어에서, 웹(Chrome과 Safari)과 macOS 앱으로 돌립니다.

1. **계산 반복:** `total = total + i * 2 - 1`을 백만 번(KNOWN_ISSUES의 프로그램)
2. **문자열:** `&`, `Mid`, `InStr`, `Len`으로 긴 문자열을 반복해서 만들고 찾기
3. **예제:** `typing`과 `quiz`를 이벤트 스크립트로 돌려, 단계마다 결과가 화면에 보이기까지의 시간
4. **작은 게임:** 폼 위의 Image 20개를 바퀴마다 조금씩 움직이고, 바퀴마다 모든 쌍이 부딪혔는지 검사하고, 점수 Label을 바꿈. 아직 Timer가 없으므로(2-9) `DoEvents`를 넣은 반복으로 30ms Timer가 할 일을 할 수 있는 한 빨리 함. 잴 것: **초당 갱신 횟수(목표 30 이상)**, 한 번 갱신에 걸리는 ms, 그 가운데 인터프리터(반복의 시작부터 `DoEvents`까지)와 그리기(Flutter의 프레임 시간: build와 raster)가 각각 얼마인지
5. **갤러그 같은 게임:** 측정 결과 다음을 보세요.

**2-2 단계에서 잰 것**(2026-10-26, `ba11bc0`의 `main`에 2-2 단계를 더한 것. 플레이어와 IDE를 측정용으로 빌드, `lib/bench_main.dart`. Chrome과 WebKit은 작성자의 맥에서 Playwright로, Safari 대신 WebKit. macOS 앱은 릴리스 빌드). 플레이어의 숫자를 먼저, IDE의 숫자를 괄호에 적습니다.

- **플레이어는 IDE만큼 빠릅니다.** 같은 인터프리터를 돌리기 때문입니다. 플레이어가 더 빠른 곳(문자열, 첫 단계)은 IDE가 자기 출력 칸과 실행 창을 다시 그리던 곳입니다.
- **typing과 quiz의 한 단계는 한 프레임 이내입니다**(7~17ms). 사용자가 한 일이 다음 프레임에 보입니다. macOS에서 플레이어의 단계는 화면의 다음 프레임(60Hz에서 16.7ms)을 기다리고, IDE는 어차피 프레임을 그리고 있어 더 일찍 옵니다.
- **느린 것은 백만 번 반복 하나뿐이고, 웹에서는 대부분 인터프리터 탓이 아닙니다.** 7.5초 가운데 3.0초가 인터프리터이고, 4.5초는 화면 갱신과 중지 단추를 위해 인터프리터가 1000번(1000바퀴마다 한 번, `_stepsPerYield`) 쉬는 데 들었습니다. 한 번 쉴 때마다 브라우저의 가장 짧은 타이머인 약 4.5ms가 걸립니다. 바퀴 수가 아니라 시간으로(10ms쯤 지났을 때) 쉬는 것은 2-2 바로 다음에 했습니다. 아래를 보세요.

**시간으로 쉬게 한 뒤**(인터프리터가 10ms쯤 지났을 때 쉼, LANGUAGE §9.1, 같은 방법으로 잼): 백만 번 반복이 **Chrome 3.3초**(전 7.5초), **WebKit 1.1초**(7.1초), **macOS 1.33초**(1.38초)이고, 플레이어와 IDE가 같습니다. 쉬는 횟수가 1000번에서 220, 82, 130번으로 줄었습니다. 작은 게임은 그대로입니다(초당 117, 179, 1870번). `DoEvents`는 전처럼 바퀴마다 쉬기 때문입니다. 동일성 테스트도 그대로입니다.

**갤러그 같은 게임**(기준 프로그램 5, `test/bench/galaga`. 2-2 다음에 더했고, 시간으로 쉬게 한 뒤에 잼): 적 40개, 내 총알 최대 10개, 적 총알 최대 10개, 내 비행기 하나, 모두 Image 61개를 바퀴마다 움직이고, 총알마다 모든 적과 비행기에 부딪혔는지 검사함(많으면 410번). 600바퀴이고, 바퀴마다 16ms Timer(초당 60번)가 하듯 `DoEvents`로 끝남. 플레이어의 숫자, 괄호는 IDE:

| | Chrome | WebKit | macOS 앱 |
|---|---|---|---|
| 초당 갱신(목표 60) | 116 (110) | 164 (145) | 1069 (1114) |
| 한 바퀴의 인터프리터 | 1.9ms (1.9ms) | 1.2ms (1.2ms) | 0.85ms (0.80ms) |

16ms 틱 가운데 인터프리터는 2ms 이하, 그리기는 7ms 이하입니다. **이런 게임에 2단계 계획보다 더 필요한 것**(아무것도 정하지 않음):

- **동시에 누른 여러 키:** `KeyDown`/`KeyUp`(2-10)은 키가 눌리고 떼질 때를 알립니다. 게임은 지금 어떤 키들이 눌려 있는지(왼쪽과 발사를 함께) 묻습니다. 예: `Keyboard.IsDown(Keys.Left)` 같은 호출
- **모든 컨트롤의 `Visible`:** 맞은 적을 폼 밖으로 옮기지 않고 숨기기
- **같은 컨트롤 여러 개:** 언어에 컨트롤 배열이 없으므로(규칙 11) 적 40개는 이름 40개와 `Left`/`Top` 80줄입니다. 실행 중 컨트롤 만들기나 번호로 컨트롤에 닿는 방법이 ROADMAP 2단계 목록에 있습니다(`Handles` 절, 실행 중 컨트롤 생성)
- **소리:** 쏠 때나 맞을 때 짧은 소리(`PlaySound("shot.wav")`). 프로젝트의 소리를 그림처럼 보관
- **그림을 차례로:** 여러 장을 차례로 보여 주는 Image(폭발, 날갯짓하는 적). IDEAS.md의 "그림 여러 장"
- **16ms Timer**(2-9)와, 한 바퀴가 길어져도 틱이 쌓이지 않게 하기. 프레임 속도와 상관없이 움직이도록 ms 단위로 시간 읽기
- **충돌 도움:** 두 컨트롤이 겹치는지 알려 주는 함수. 검사 하나가 호출 하나가 됨

**플레이어의 크기**(릴리스 빌드, hello 프로젝트를 넣은 것): **웹**은 폴더로 42MB이고, 그 가운데 36MB가 브라우저마다 다른 CanvasKit 빌드입니다. 브라우저가 받는 것은 약 11MB(`main.dart.js` 2.8MB, CanvasKit 하나 7MB, Pretendard 1.6MB)이고, `.zip`으로 15MB입니다. **macOS**는 43MB(유니버설), `.zip`으로 19MB입니다. **Windows**는 Visual C++ 런타임을 실행 파일 옆에 둔 폴더로 29.5MB입니다(빌드마다 CI가 알려 줍니다. IDE의 폴더는 36MB). 비교하면 IDE는 macOS에서 51MB, `main.dart.js` 3.4MB입니다.

**기준.** 플레이어에서, 웹이나 macOS 가운데 어디서든 다음이 되면 트랜스파일러를 다시 계획합니다(결정 2).

1. **작은 게임의 인터프리터가 한 바퀴에 10ms를 넘을 때**(30ms 틱의 3분의 1. 지금은 0.39~0.93ms)
2. **typing이나 quiz 예제의 한 단계가 첫 단계 다음에 50ms를 넘을 때**(지금은 많아야 26ms)
3. **백만 번 반복의 인터프리터 부분이 6초를 넘을 때**(Chrome의 오늘 3.0초의 두 배), 또는 학생의 실제 프로그램이 너무 느리다는 것이 확인될 때

다만 아래처럼 인터프리터를 빠르게 한 뒤에도 기준을 넘을 때만입니다. 인터프리터의 속도를 바꿀 때마다 기준 프로그램을 다시 잽니다.

**느린 곳이 인터프리터라면** 트랜스파일러보다 다음을 먼저 합니다. 모두 결과가 같다고 증명되는 곳에서만 합니다(규칙 4는 동작을 바꾸는 빠른 길을 금하고, 판정은 패리티 테스트가 합니다).

- **시간으로 쉬기**(함): 화면 갱신을 위한 쉼을 1000바퀴마다가 아니라 10ms쯤 지났을 때 합니다. 웹에서는 반복 시간의 가장 큰 부분이었습니다(위).
- **이름을 미리 풀기:** 분석기는 이미 모든 변수를 압니다. 쓸 때마다 이름으로 찾지 않고 변수마다 칸 번호를 줍니다.
- **문장 묶음을 동기로:** 사용자 프로시저 호출도, `DoEvents`·`MsgBox`·`InputBox`도 없는 문장 묶음은 기다릴 일이 없습니다. 문장마다 `await`하지 않고 처리해도 순서는 똑같습니다(D25가 이미 식에서 그렇게 함).
- **속성 바꾸기를 모아서:** 한 바퀴 안의 많은 `Left`/`Top` 변경을 하나하나 알리지 않고, 다음 프레임에 한 번 다시 그립니다.
- **컨트롤 찾기를 줄이기:** 속성에 접근할 때마다가 아니라 처리기마다 한 번 컨트롤 상태를 찾습니다.

느린 곳이 그리기라면 런타임의 위젯을 봅니다(움직인 것만 다시 그리기). 이것은 트랜스파일러로도 바뀌지 않습니다.

## 8. 위험 요소

- **macOS:** 넣은 파일 때문에 서명이 깨지면 앱이 실행되지 않습니다. 다시 서명은 묶음 전체를 덮어야 하고, Developer ID가 없으므로 Gatekeeper는 여전히 "그래도 열기"를 요구합니다. 프로젝트는 앱 옆이 아니라 앱 안에 넣어, 앱 하나만 복사하면 되게 합니다.
- **Windows:** 인터넷에서 받은 서명 없는 프로그램은 SmartScreen과 일부 백신이 경고할 수 있습니다. 릴리스 노트에 이미 적었습니다.
- **버전:** 어느 IDE 버전이 내보낸 앱과 다른 버전의 플레이어가 모르는 사이에 만나면 안 됩니다. 묶음의 형식 버전과 플레이어의 버전을 확인하고, IDE는 자기 버전의 틀을 받습니다.
- **속도:** 무거운 반복은 네이티브 앱보다 느립니다. 초보자가 쓰는 크기의 프로그램에서는 느끼지 못합니다(KNOWN_ISSUES). 느끼는 프로그램이 나오면 그것이 결정 2의 계기입니다.
- **웹 앱에는 웹 호스트가 필요합니다:** 디스크의 `index.html`을 바로 열면 브라우저에서 동작하지 않을 수 있습니다. 2-4 단계에서 확인하고, 내보내기가 올리는 방법을 알려 줍니다.
- **소스가 앱 안에 들어갑니다:** 누구나 읽을 수 있습니다. 앱이 퍼져 나가면 비밀 키 경고(DESIGN §11)가 더 중요해집니다.
- **실행 창 하나, 앱 둘:** 2-1 단계의 옮기기가 IDE를 바꾸면 안 됩니다. IDE의 테스트가 그 지킴이입니다.
